# Memory

Persistent, per-role memory kept as plain markdown. You — the agent — read
and write these files yourself, directly, with your `Read`, `Write`, `Edit`,
and `Glob` tools. There's no CLI wrapper, no script, nothing shell-path-
dependent to break. It works the same on any host, from any working
directory, whether or not the Octobots supervisor happens to be running.

## File layout

Everything lives under `.agents/memory/<role>/`, where `<role>` is whatever
your agent's `name:` frontmatter says — `project-manager`, `python-dev`,
`scout`, and so on:

```
.agents/memory/<role>/
├── MEMORY.md                ← curated index, one line per entry
├── <slug>.md                ← individual curated entries (frontmatter + body)
├── project_briefing.md      ← seeded by scout at install time (type: project)
├── daily/
│   └── YYYY-MM-DD.md        ← episodic daily logs, append-only
└── snapshot.md              ← auto-generated by supervisor (may be absent)
```

The first time you need any of these directories, create them with
`mkdir -p`. Leave `snapshot.md` alone — it belongs to the supervisor's
launch hook, not to you. If it isn't there at all (stock Claude Code, no
supervisor attached), that's expected — just read memory directly instead.

`.agents/` was chosen deliberately as an IDE-neutral path, so this same
memory layout holds up whether the agent is running under Claude Code,
Cursor, Gemini CLI, Windsurf, Copilot CLI, or under the Octobots
supervisor.

## Legacy paths (one-time migration)

If you come across memory sitting in one of the older locations below, and
`.agents/memory/<role>/` doesn't exist yet, migrate it before you write
anything new:

| Old location | New location |
|---|---|
| `.claude/memory/<role>/` (directory) | `.agents/memory/<role>/` — move the whole dir |
| `.octobots/memory/<role>/` (directory, from Octobots supervisor) | `.agents/memory/<role>/` — move the whole dir |
| `.claude/memory/<role>.md` (flat file, from old project-seeder) | `.agents/memory/<role>/project_briefing.md` — wrap the existing content with `type: project` frontmatter (see "Write" op below), add one index line to `MEMORY.md` |

Use `Bash` for the directory moves (`mv`) and `Read`/`Write` for converting
the flat file into a curated entry. This is a one-time job — once it's done,
ignore the old paths going forward.

## Two stores, two purposes

| Store | When to use | Cost | Example |
|---|---|---|---|
| **Daily log** | Anything today's you would want tomorrow's you to know. Episodic, transient, cheap. | 1 line appended | "User pushed back on adding a new flag; wants to reuse existing config key" |
| **Curated entry** | Durable facts, preferences, decisions, references. Should still be useful in 6 months. | 1 index slot | User's timezone; a validated correction about testing strategy |

**Not sure which one? Log it.** A daily-log line can always be promoted to
a curated entry later — but never go the other direction.

## Four curated types

Every curated entry carries a `type:` field:

| Type | Holds |
|---|---|
| `user` | Who the user is — role, expertise, preferences, working style |
| `feedback` | Corrections and validated approaches. Always include *why* |
| `project` | Goals, deadlines, constraints, in-flight initiatives. Decays fast — re-verify before acting. **Scout seeds one here at install time (`project_briefing.md`)** covering stack, conventions, and role-specific gotchas. |
| `reference` | Pointers to external systems (Linear projects, Slack channels, dashboards) |

## Operations

### Log — append to today's daily log

To record `<text>`, follow these steps:

1. Determine today's date. Use the `Today's date is …` line in your
   environment context. If not present, run `date -u +%Y-%m-%d`.
2. Target path: `.agents/memory/<role>/daily/<today>.md`.
3. If the file **does not exist**, `Write` it:
   ```
   # Daily log — <today>

   - [HH:MM] <text>
   ```
4. If the file **already exists**, `Edit` to append a single new line at
   the end: `- [HH:MM] <text>`.

Stick to 24-hour `HH:MM`, one observation per line. Keep it terse — a full
sentence is fine, but a paragraph belongs in a curated entry instead.

### Write — create or replace a curated entry

To record a curated entry named `<name>` with a given `<type>`,
`<description>`, and `<content>`:

1. **Slugify** `<name>`: lowercase it, swap non-alphanumeric characters for
   `_`, and strip leading/trailing underscores. So `User Timezone` becomes
   `user_timezone`.
2. **Target path**: `.agents/memory/<role>/<slug>.md`.
3. **`Write`** the file using exactly this frontmatter (the supervisor's
   snapshot regenerator parses out `name`, `description`, and `type` — none
   of the three can be omitted, no extra keys get added, and each stays on
   its own line):
   ```markdown
   ---
   name: <name>
   description: <description>
   type: <type>
   ---

   <content>
   ```
4. **Update the index** at `.agents/memory/<role>/MEMORY.md`:
   - **If `MEMORY.md` doesn't exist yet**, `Write` it:
     ```markdown
     # Memory index — <role>

     - [<name>](<slug>.md) — <description>
     ```
   - **If a line already points at `<slug>.md`**, `Edit` just that line to
     carry the new description — one entry, one line, never duplicated.
   - **Otherwise**, `Edit` the file to append a new line at the end:
     `- [<name>](<slug>.md) — <description>`.

### Read — recall memory on demand

1. **If a snapshot was already auto-imported** (look for the
   `@.agents/memory/<role>/snapshot.md` line near the top of your
   AGENT.md), curated memory and the recent daily logs are already sitting
   in your context — there's no need to re-read them.
2. **If no snapshot was loaded** (stock Claude Code, or this is the first
   session on a fresh project), read memory directly instead:
   - `Read .agents/memory/<role>/MEMORY.md` for the curated index.
   - `Read .agents/memory/<role>/<slug>.md` for whichever entry the index
     points you toward. Scout's `project_briefing.md` tends to matter most
     on a brand-new project.
   - `Glob .agents/memory/<role>/daily/*.md`, sort the results by filename
     descending, and `Read` the 3 most recent files.

Keeping recall bounded like this is what keeps your context small — don't
tail through the entire daily-log history.

### Rename / delete

- **Rename** a curated entry by `Write`-ing the new `<new-slug>.md`,
  removing the old file, and `Edit`-ing `MEMORY.md` to replace that one
  line.
- **Delete** by removing `<slug>.md` and `Edit`-ing `MEMORY.md` to drop its
  line.
- **Never go back and edit a daily-log entry.** Log a correction as a
  new line instead — the audit trail is the point.

## What belongs in memory vs. somewhere else

- **Memory** covers durable facts and short-lived working notes that
  matter *to you, the agent* across sessions — user preferences, project
  constraints, lessons pulled from corrections, pointers to external
  systems.
- **Not memory** is anything a human besides you would need to find.
  That belongs in the user's knowledge base (`obsidian-vault`, say), in
  the project's docs, in the issue tracker, or in the code itself.

A few agents also stash role-specific operational state in this same
directory (personal-assistant's `people-pending.md` is one example).
That's fine — you're free to extend the layout, as long as `MEMORY.md`,
`<slug>.md`, and `daily/` still follow the spec above.

## Snapshot.md — supervisor concern, not yours

`snapshot.md` gets regenerated by the Octobots supervisor's launch hook
(`supervisor/skills/memory/scripts/memory.py snapshot`) right before each
role spawns. It folds `MEMORY.md`, the body of every curated entry, and the
last 3 days of daily logs into one file, which the agent's `AGENT.md` then
auto-imports through `@.agents/memory/<role>/snapshot.md`.

Writing `snapshot.md` is never your job. If it happens to be missing, the
`@import` simply becomes a no-op and you fall back to reading on demand —
no error, nothing interrupted. Stock Claude Code users work under the exact
same memory model; the only thing they lose is the free auto-load at
session start.
