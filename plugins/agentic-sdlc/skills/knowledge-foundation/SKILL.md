# knowledge-foundation

Onboards a project for AI-assisted development. Calls or consumes a read-only `knowledge-auditor` audit, proposes a guide-generation, incorporation, and merge plan, gets user approval, generates the `.agentic/guides/` guide set, and wires it into the project's AI entrypoint file.

**Never auto-installs superpowers or any other tooling.** Uses `superpowers:brainstorming` and `superpowers:dispatching-parallel-agents` if the host AI tool exposes them; otherwise falls back to the host's native subagent capability (e.g., the Agent tool with `subagent_type: "general-purpose"` in Claude Code).

## Phases

```
Phase 1: Audit           → Phase 2: Plan & Approve  (HARD GATE)
                                ↓
                          Phase 3: Generate
                                ↓
                          Phase 4: Wire entrypoint   (GATE on diff per target file)
                                ↓
                          Phase 5: Validate & report
```

Each phase loads its own reference doc only when entering that phase.

## Output Rule

All project guidance generated by this skill is written under `.agentic/guides/`.
Do not write or maintain a parallel documentation guide tree outside `.agentic/guides/`.
`.agentic/guides/` is the single source of truth consumed by agentic-sdlc skills and agents.
`AGENTS.md` is the canonical generated assistant entrypoint. When a project also
uses Claude Code, `CLAUDE.md` should be a minimal shim that imports `AGENTS.md`
with `@AGENTS.md`; do not duplicate guide tables, task classifiers, commands, or
project rules in `CLAUDE.md`.

## Phase 1 — Audit

**Goal:** Run or consume `knowledge-auditor` as the first action, then derive planning inputs from its read-only report. No writes.

Load `references/detection.md` before doing any repository analysis. The first action after loading it is to invoke `knowledge-auditor` or validate a supplied `# Knowledge Audit Report`; only then derive the project shape, modules, AI tool targets, tech stack per scope, categories with evidence, and confidence levels needed by later phases.

Phase 1 output must include the audit's `Documentation Map`, `Documentation Analysis`, `Assistant Setup Analysis`, `Agentic Infrastructure Analysis`, `Conflict And Overlap Analysis`, `Foundation Readiness And Next Steps`, and `Evidence Appendix`. Treat those sections as the source of truth for documentation quality, existing agentic infrastructure, conflicting assistant setups, and whether foundation should preserve, incorporate, merge, replace, skip, ask the user, or halt.

**No writes are allowed until the audit is complete, the Phase 2 incorporation and merge plan is presented, and the user explicitly approves that plan.**

**Halt before Phase 2** if any of:
- Tech-stack confidence < 80%.
- The audit reports a `halt` recommendation.
- The audit reports unresolved `conflicting` evidence that affects guide generation, command selection, or entrypoint wiring.
- No AI-tool signals AND user declines to choose a target.
- Repo is empty (no manifests, no source files).

## Phase 2 — Plan & Approve  (HARD GATE)

**Goal:** Build an audit-grounded guide-generation, incorporation, and merge plan from Phase 1 output and get explicit user approval.

Load `references/planning.md` and follow it.

- If `superpowers:brainstorming` is in the available skills list, invoke it via the Skill tool to drive the conversation.
- Otherwise present the plan inline using the format in `planning.md`.
- **Do not auto-install superpowers.**

Wait for the user to say "approve" / "yes" / "go" before proceeding. Customize loop is fine; cancel halts the run.

**No writes are allowed before this phase completes with explicit approval of the audit-grounded incorporation and merge plan.**

## Phase 3 — Generate

**Goal:** Render approved guides into `.agentic/guides/`.

Load `references/generation.md` and follow it.

- Single repo: render in main session, write to `.agentic/guides/<category>/<file>.md`.
- Monorepo: dispatch one subagent per module, all in **one message** for parallel execution. Each module still writes its guide output under that module's `.agentic/guides/` tree.
  - Use `superpowers:dispatching-parallel-agents` if available.
  - Otherwise call the Agent tool directly with `subagent_type: "general-purpose"`, one call per module, in the same message.
- Each subagent returns a structured summary; main session aggregates.

Honor:
- Placeholder contract (`[NAME]` required, `[NAME?]` drop-row).
- Content-style rule (practices > code dumps; bad/best contrast tables; `file:line` references).
- Size caps from `references/knowledge-craft.md`; generated guides have hard maximums, no minimum line count, and must not be padded with reminder/filler lines.

After all `.agentic/guides/` content is written, run the following steps to generate project-specific SDLC guide files.

### Step A — Project context → `.agentic/guides/project.md`

Detect defaults before prompting:
- Project/package name from manifests (`package.json`, `pyproject.toml`, `pom.xml`, etc.).
- Repository remote and source-control provider from `git remote -v`.
- Default target branch from repository docs, CI, remote metadata, or `main` as a fallback.
- Work-item tracker provider and key/prefix from existing docs, branch names, commits, or user input.
- Ticket adapter status, lookup/create operations, and output format from project docs, existing assistant skills, MCP configuration, or user input.

Ask only for missing or conflicting values needed to fill this schema:
1. Project name and repository/package name.
2. Project code/key, if configured; use `none` if not configured.
3. Work-item tracker provider and key/prefix — use `ticket_detection.provider` and `ticket_detection.key_prefix`; prompt only if `confidence` is `low` or `none`.
4. `## Ticket Adapter` status, adapter, lookup, create, and output contract — populate from `ticket_detection`; when `confidence` is `high`, present the pre-filled values to the user for confirmation rather than asking open-ended questions; use `not configured` only when `ticket_detection.adapter_source === "none"` and no user correction is given.
5. Source-control/review provider (for example GitLab or GitHub), repository remote, default target branch, and review artifact type (`MR` or `PR`).
6. `## MR Adapter` status and instructions; use `not configured` if absent.

Write `.agentic/guides/project.md` using exactly this schema and no extra routing sections:
```markdown
# Project Context

## Project Identity

| Field | Value | Source |
|---|---|---|
| Project name | [value] | [file:line or user decision] |
| Repository/package | [value] | [file:line or user decision] |
| Project code/key | [value or none] | [file:line or user decision] |

## Work Item Tracker

| Field | Value |
|---|---|
| Provider | [Jira/GitHub Issues/Linear/none/etc.] |
| Key/prefix | [value or none] |

> Adapter configuration belongs exclusively in `## Ticket Adapter`. Do not duplicate adapter status or instructions in the Work Item Tracker table.

## Ticket Adapter

**Status**: configured | not configured
**Adapter**: [skill, MCP server, command, tool instructions, or not configured]
**Lookup**: [exact lookup operation that returns summary, description, acceptance criteria, and links, or not configured]
**Create**: [exact create operation; must pass a complete story/work-item payload or file artifact, never a conversational reference such as "as drafted"]
**Output**: [ticket key or URL returned by the adapter, or not configured]

> **Schema enforcement:** The `## Ticket Adapter` section MUST contain only these five fields: `**Status**`, `**Adapter**`, `**Lookup**`, `**Create**`, `**Output**`. Never add extra fields (e.g. `**Underlying command**`, `**Multi-turn follow-up**`, `**Notes**`). Phase 5 validates this.

## Source Control And Review

| Field | Value |
|---|---|
| Provider | [GitLab/GitHub/other] |
| Repository remote | [remote URL or not detected] |
| Default target branch | [branch] |
| Review artifact type | MR | PR |

## MR Adapter

**Status**: configured | not configured
**Adapter**: [CLI, MCP server, command, tool instructions, or not configured]
**Instructions**: [extra adapter usage instructions or not configured]
**Body Template**: [optional MR/PR body template, or omit when not configured]
```

Redistribute drift instead of adding it to `project.md`:
- Branch naming, commit format, merge strategy, ticket-in-commit behavior, and review-title conventions belong in `.agentic/guides/standards/git-workflow.md`.
- Exact lint, format, build, test, security, coverage, and verification commands belong in `.agentic/guides/quality-gates.md`.
- Task routing and guide selection belong in the entrypoint managed regions.
- Package boundaries and ownership belong in architecture or tool guides.
- Validation reporting policy belongs in `quality-gates.md` or the entrypoint.

`project.md` must not include related-guides sections, task routing, branch/commit examples, quality-gate commands, evidence-index padding, or reminder/filler lines. The dedicated `## Ticket Adapter` section is required because product-owner and requirements-intake read it directly. The dedicated `## MR Adapter` section is required because MR/PR skills read it directly.

### Step B — Git conventions → `.agentic/guides/standards/git-workflow.md`

Before prompting, detect from existing project files:
- Run `git log --oneline -10` to detect commit message pattern (look for `PREFIX-NNN:` style)
- Check `.pre-commit-config.yaml` for commit-msg hooks
- Check CI files (`.github/workflows/`, `.gitlab-ci.yml`) for branch name patterns

Then prompt (present the detected value as the default if found):
1. "What is your branch naming pattern?" (e.g. `PROJ-XXXX_description` or `feature/description`)
2. "What is your commit message format?" (e.g. `PROJ-XXXX: Description`)
3. "What merge strategy does your team use?" (options: squash / rebase / merge commit)

Write `.agentic/guides/standards/git-workflow.md` using the confirmed values throughout — replace placeholder examples with real patterns using the actual project key. The file must contain these sections:
- **Branch Naming Convention** — pattern with examples using real key
- **Commit Message Format** — format string with examples
- **Merge Strategy** — chosen strategy and rationale
- **Anti-Patterns** — bad vs good table using real project key
- **Troubleshooting** — common issues and fixes

### Step C — Quality gates → `.agentic/guides/quality-gates.md`

Scan the following sources in order for quality gate candidates:
1. `Makefile` targets — look for targets matching: lint, format, ruff, test, pytest, coverage, gitleaks, sonar, license, type-check, mypy
2. `pyproject.toml` — `[tool.ruff]`, `[tool.pytest.ini_options]`, `[tool.mypy]` sections; `[project.scripts]`
3. `package.json` — `scripts` field
4. `.pre-commit-config.yaml` — hooks
5. CI files (`.github/workflows/*.yml`, `.gitlab-ci.yml`, `Jenkinsfile`) — job steps
6. `tox.ini`, `setup.cfg`

For each gate type (lint, format, type-check, test, secret-scan, license-check, static-analysis):
- Collect all candidate commands found across sources
- If one candidate: present it with source and reasoning, ask "Include this gate? (yes/no/modify)"
- If multiple candidates: present all with source and reasoning, propose the best one (prefer Makefile targets over direct tool commands), ask user to confirm or choose

After all gate types are confirmed, write `.agentic/guides/quality-gates.md`:
- One `###` section per gate, ordered fastest-to-slowest
- Each section contains:
  - **Run**: the exact command
  - **Pass**: what a passing run looks like
  - **Fail**: what a failing run looks like and what it means
  - **Auto-fix** (if applicable): the fix command
  - **Skip if** (if applicable): condition under which the gate may be skipped with a warning

## Phase 4 — Wire entrypoint  (GATE per target file)

**Goal:** Idempotently update guide imports + task classifier + critical rules + commands in the project's AI entrypoint file(s).

Load `references/entrypoint-merge.md` and follow it.

- If multiple targets were detected in Phase 1, produce one diff per file, gated independently (one approval per file, not bulk).
- Always show the diff to the user before writing.
- Outside managed regions: **never touch** existing content.
- Prefer `AGENTS.md` as the primary managed entrypoint. If `CLAUDE.md` is also
  targeted, render it as a minimal Claude Code shim containing only the managed
  `@AGENTS.md` import and remove/replace legacy generated Claude guidance after
  showing the per-file diff and receiving approval.

## Phase 4A — Ignore local run state

**Goal:** Keep agentic-sdlc local run journals out of commits.

Before validation, ensure the repository ignores `.agentic/runs/`:
- Read `.gitignore` if it exists; create it only after the Phase 2 write plan is approved.
- Add `.agentic/runs/` if it is missing.
- If a previously generated `.agentic/runs/<branch>.json` file exists and is untracked, remove it from the worktree after adding the ignore rule.
- If `.agentic/runs/<branch>.json` is already tracked, do not remove it silently; report it and ask the user whether to untrack it.

## Phase 5 — Validate & report

**Goal:** Verify outputs and produce a final report.

Run these checks (no silent auto-fix; if any fails, list it and ask user how to proceed):

| Check | How |
|---|---|
| All referenced guide paths resolve | Read each path in the entrypoint table |
| All `file:line` refs in guides resolve | Read the file, verify line ≤ length |
| No `[PLACEHOLDER]` / `[PLACEHOLDER?]` tokens remain | grep generated files |
| Each guide is concise and no more than 400 lines | `wc -l` |
| Entrypoint is concise, reference-only, and no more than 300 lines | `wc -l` |
| `.agentic/runs/` is ignored | `git check-ignore -v .agentic/runs/` or inspect `.gitignore` |
| Claude entrypoint is shim-only when AGENTS.md exists | `CLAUDE.md` contains `@AGENTS.md` and no duplicated generated guide tables |
| No reminder/filler padding exists | reject `Review reminder`, `Foundation reminder`, `Operating reminder`, repeated near-identical lines, and placeholder rows |
| `project.md` follows Project Context schema | verify only Project Identity, Work Item Tracker, Ticket Adapter, Source Control And Review, and MR Adapter sections are present |
| `## Ticket Adapter` contains only Status, Adapter, Lookup, Create, Output fields | grep for any `**` field not in that set |
| `**Adapter**` value references a skill or MCP invocation, not an internal CLI command | grep for `--` flags, binary path patterns (e.g. `assistants chat`), or non-Skill-tool invocation patterns |
| Drift content is redistributed | git conventions in `git-workflow.md`, exact commands in `quality-gates.md`, routing in entrypoint |
| Discovered commands match manifests | re-read `package.json`/`Makefile`/etc. |
| Managed regions have matching markers | grep for `start`/`end` pairs |

Final report (markdown) lists per-scope guide counts, skipped categories with reason, entrypoint files written/merged.

## What this skill does NOT do

- Does not install superpowers or any other tooling.
- Does not run lint/build/tests on the target project.
- Does not write code outside `.agentic/guides/` (or `<module>/.agentic/guides/`), the chosen entrypoint file(s), and the `.gitignore` rule for `.agentic/runs/`.
- Does not perform git operations.
- Does not modify the `/agentic-init` skill (`plugins/agentic-os/skills/agentic-init/`) or its templates.

## Phase 6 — Write Run Journal

Read `.agentic/runs/<branch>.json` where `<branch>` is the output of
`git branch --show-current`. Create the file if it does not exist.

This file is local run state. It must be covered by the `.agentic/runs/` ignore
rule before the final report, and it must not be presented as a commit artifact.

Append or update the entry for this step:

```json
{
  "step": "00",
  "agent_skill": "knowledge-foundation",
  "primitive": "skill",
  "started_at": "<ISO8601 start time>",
  "completed_at": "<ISO8601 now>",
  "status": "completed",
  "outcome": "Generated <N> guides under .agentic/guides/, created project context + git-workflow.md + quality-gates.md, wired imports into <entrypoint-file>.",
  "artifacts": [
    ".agentic/guides/",
    ".agentic/guides/project.md",
    ".agentic/guides/standards/git-workflow.md",
    ".agentic/guides/quality-gates.md",
    "<entrypoint-file>"
  ],
  "next_step": "sdlc-start or product-owner"
}
```

Write the file before presenting the handoff prompt, then leave it ignored by
git. If the user asked not to keep local run journals in the worktree, remove
the generated run journal after writing the final status data and report that it
was removed.

## Phase 7 — Handoff

```
---
✅ knowledge-foundation complete.

**Outcome**: Generated <N> guides, project context, git-workflow.md, and quality-gates.md. Entrypoint file updated.

**Recommended next step**:
- Story exists or task is ready → invoke the `sdlc-start` skill
- Raw idea still needs a story → invoke the `product-owner` skill

How would you like to proceed?
- **yes / proceed** → I'll invoke the recommended skill now
- **no / skip** → stop here, I'll wait for your instruction
- **other** → tell me what to do instead
```
